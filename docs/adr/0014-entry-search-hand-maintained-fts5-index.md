# 0014: Entry search — a hand-maintained FTS5 index, not triggers on an external-content table

## Status

Accepted

## Context

Ticket #37 gives `EntryStore` a `search()` that finds Entries by a prefix of a word in their body,
takes the query text literally no matter what it contains, and stays correct through the store's
existing write paths — Send and Sync both arrive through `upsert()`, and Entries are immutable and
never deleted (see the domain glossary), so the index only ever needs to gain rows, never update or
drop one.

SQLite's FTS5 module is the natural fit for prefix search, and it offers a shortcut for keeping an
index in sync automatically: an *external-content* table, which stores no data of its own and
instead reads it from a regular table via triggers, bound to that table's `rowid`. That shortcut
doesn't fit here. `entries.id` is `TEXT PRIMARY KEY`, not `INTEGER PRIMARY KEY` — SQLite doesn't
alias it to the table's `rowid`, so `entries` still has its own implicit, SQLite-managed `rowid`
that the schema never names. That rowid isn't guaranteed stable (`VACUUM` can renumber it), and an
external-content FTS5 index's rows are keyed by exactly that value. A trigger-maintained index built
on that binding would drift silently the first time SQLite renumbered a row: the index would keep
pointing at whatever `rowid` it was given at insert time, now holding someone else's Entry.

## Decision

**`entries_fts` is a standalone FTS5 table, not external-content, storing its own copy of `id`
(unindexed) and `body`.** It has no `rowid` binding to `entries` at all, so `entries`'s `rowid`
being renumbered can't desynchronize it. Search joins the two tables explicitly on `id`:

```sql
SELECT entries.* FROM entries_fts JOIN entries ON entries.id = entries_fts.id
WHERE entries_fts MATCH ? ORDER BY entries.created_at DESC, entries.id DESC
```

**The index is maintained by the store's write path, not by a trigger.** `SqliteEntryStore.upsert()`
— the one place Entries arrive, from both Send and Sync — inserts each Entry into `entries_fts`
after writing it to `entries`, guarded by `INSERT ... WHERE NOT EXISTS (SELECT 1 FROM entries_fts
WHERE id = ?)`. That guard is the whole story: since Entries are immutable, the index never needs an
`UPDATE`, and since Sync can redeliver an Entry this Device already has, the guard is what keeps a
redelivery from inserting a second row for the same `id`. No transaction wraps it, for the same
reason ADR 0007 gives for `entries` itself — it's a single idempotent statement, not a multi-step
write that can partially apply.

**The migration backfills existing Entries with the same guard.** `entries_search_index.sql` creates
the virtual table, then runs:

```sql
INSERT INTO entries_fts (id, body) SELECT id, body FROM entries
WHERE id NOT IN (SELECT id FROM entries_fts);
```

The migration runner (`migrator.ts`) wraps nothing in a transaction and relies on every statement
being safe to re-run (ADR 0007) — a process that dies after this statement but before its ledger row
is written would otherwise re-insert every backfilled Entry on retry. `WHERE id NOT IN (...)` is
the explicit guard that keeps that safe.

**This migration is hand-written, not generated by `drizzle-kit generate`, and isn't tracked in
`meta/`.** An FTS5 virtual table isn't representable in `schema.ts`'s ORM-mapped tables, so there is
nothing for `drizzle-kit` to diff or generate here. Its file is named `entries_search_index.sql`
rather than with drizzle-kit's `NNNN_` convention, specifically so a future *real* `generate` run
(triggered by an actual `schema.ts` change) can't collide with it on a number. `meta/` keeps
describing only what `schema.ts` declares — `entries_fts` doesn't appear there, and shouldn't.

**Search reads and writes for `entries_fts` go through the raw `SqliteDriver`, not the drizzle query
builder.** `SqliteEntryStore` already holds the driver it was constructed with; `search()` and the
index-maintenance call use `driver.execute()` directly with hand-written SQL and manual positional
row mapping, the same shape `migrator.ts` already uses for its ledger table. Routing a virtual
table's `MATCH` operator through drizzle's query builder would work, but only by fighting it — the
builder has no typed notion of `MATCH`, so it would end up as a `sql` fragment threaded through
`.where()` regardless. Using the driver directly is the same amount of raw SQL with less machinery
between it and what actually runs.

**The query text is always escaped into a single quoted, prefix-matched phrase.** FTS5 query syntax
recognizes `AND`, `OR`, `NOT`, column filters, and parentheses *outside* a quoted string, but treats
everything *inside* one as literal text to tokenize — never as syntax. `search()` builds its MATCH
expression as `"<query, with every " doubled>"*`: doubling `"` is FTS5's own escape for a literal
quote inside a quoted string, and it keeps the result balanced no matter what the user typed, so it
can't throw a syntax error. The trailing `*` makes the phrase's last token a prefix match — FTS5's
built-in behavior for a quoted string immediately followed by `*` — which is what gives `recur` a
match on "recurring" without any bespoke tokenization code. An empty or whitespace-only query is
special-cased to return no results before this construction runs, rather than asking FTS5 to match
an empty phrase.

**No `prefix=` index-time configuration.** FTS5 supports declaring prefix indexes at table-creation
time as a query-speed optimization, at the cost of extra index storage per configured prefix length.
Meologue's History is one person's captured thoughts, not a corpus large enough for a full table
scan under a `*` prefix query to matter — see the [[v01-scope-discipline]] pattern of not building
for scale nobody has yet. If this stops holding, `prefix=` is an additive change to the `CREATE
VIRTUAL TABLE` statement in a future migration, not a rearchitecture.

**SQLite 3.46 is the compatibility floor**, because the four runtimes involved genuinely differ and
none of them are pinned to the same build:

- The Node driver used only by tests (`node:sqlite`) bundles 3.53.4.
- The web target (`@sqlite.org/sqlite-wasm`) is pinned to 3.53.0.
- Android (`@capacitor-community/sqlite`, backed by SQLCipher) bundles its own SQLite build.
- macOS links Apple's **system** `libsqlite3`, not a bundled one — `tauri-plugin-sql`'s `sqlite`
  feature enables `sqlx/sqlite` without `sqlx-sqlite`'s `bundled` feature, so `libsqlite3-sys`
  resolves the library via `pkg-config`/`vcpkg` against whatever the OS provides. That version
  moves only when the OS does, and is the oldest of the four (3.51.0 on the machine this was
  verified against) — a feature that exists on 3.53 but not 3.46 would pass every test here (Node's
  newer bundle) and only fail on a real Mac, at migration time, which is exactly the failure mode
  worth naming a floor to avoid.

Nothing this ticket uses postdates 3.46: FTS5 itself, its default `unicode61` tokenizer, and the
quoted-phrase-with-trailing-`*` prefix syntax all predate it by years, and SQLite 3.46.0's own
release notes add no FTS5 features. Verified on the macOS build and the Android build on a physical
device, since the migration — not the store's TypeScript — is the part no automated test can catch.

## Alternatives considered

- **External-content FTS5 table plus `INSERT`/`UPDATE`/`DELETE` triggers on `entries`.** Rejected:
  binds the index to `entries`'s implicit `rowid`, which can be renumbered independently of the
  Entry `id`s it's supposed to track — see Context above. Also more machinery than three trigger
  bodies buy here, given Entries are immutable and never deleted, so `UPDATE`/`DELETE` triggers
  would exist only to do nothing.
- **`LIKE '%query%'` or `GLOB` against `entries.body` directly, no separate index.** Rejected: no
  word-boundary or prefix semantics without hand-rolled tokenization, and no index support — every
  search is a full table scan of every Entry's body, forever, with no incremental cost model as
  History grows.
- **Configure FTS5's `prefix=` at index-creation time.** Rejected for now — see the `prefix=`
  decision above. Extra index storage for a query-speed win this dataset size doesn't need yet.
- **Route `entries_fts` through drizzle's query builder, declaring it as an ordinary `sqliteTable`
  for query-building purposes only.** Rejected: `MATCH` has no typed representation in the builder,
  so it becomes a raw `sql` fragment regardless — declaring a fake ORM table just to join through
  it adds a layer without removing any raw SQL.

## Consequences

Adding a future migration that changes `entries_fts`'s schema (a different tokenizer, `prefix=`)
follows migration 1's shape: `CREATE VIRTUAL TABLE IF NOT EXISTS` can't be edited in place once
shipped, so a schema change means dropping and recreating the table and re-backfilling, not editing
`entries_search_index.sql`. If Entries ever stop being immutable (see ADR 0007's note that editing
requires a wire-contract and server migration regardless), `indexForSearch` in
`sqlite-entry-store.ts` needs an `UPDATE` path — today it has none because none is reachable.
`InMemoryEntryStore`'s `search()` reimplements FTS5's quoted-phrase-prefix matching in plain
TypeScript rather than sharing logic with the real store, since the two have no code in common to
share; the shared contract suite (`test-support/entry-store-contract.ts`) is what keeps their
behavior in step, the same as every other `EntryStore` guarantee.
