# Ledger audit — code vs. corpus, 2026-09-11

A row-by-row audit of **all 119 ledger rows**, reading the implementation against the reference
documents. Companion to `pass2-2026-09-11.md`, which carries the fresh Todoist measurements this
audit tests rows against.

**Why this exists.** Before this audit the ledger read **19 `matched` against 60 `built`** across
119 rows. `built` means "implemented, never driven side-by-side against Todoist" — so a row can
read healthy while the feature diverges.

> **Counting note.** Earlier drafts of this document quoted "34 matched / 62 built". That was
> wrong: it counted every backticked status word in the file, including the status-vocabulary
> table and inline mentions inside Note columns. The figures here count the **status column of
> row lines only**, which is the only count that means anything.

**Outcome.** After applying this audit's factual corrections the ledger reads **71 `built`,
17 `matched`, 16 `todoist-captured`, 12 `blocked`, 8 `divergent`** across 124 rows (5 rows added
for divergences nothing tracked). Note that `matched` **fell**, 19 → 17: `ROW-03` and `QA-01` were
overclaiming and were demoted. An audit that only ever moves rows upward is not auditing.
The user's standing complaint is that the app doesn't *feel* like Todoist despite the ledger
looking fine. This audit is the attempt to find out which rows are actually wrong.

**Method.** Eleven prefixes across five parallel read-only passes (`DATE`/`PRI`/`THEME`,
`ROW`/`DET`/`NAV`, `QA`, `SCHED`, `CMT`/`STR`/`KBD`). Every divergence below cites a file and line.
Items marked **[parent-verified]** were re-checked directly rather than taken on an agent's word;
one agent claim was found wrong that way and is recorded in "Corrections" at the end.

## 2. Rows marked `matched`/`built` that overclaim

- **`ROW-03`** (`matched`) — the ledger's own bar requires agreement on behavioural, **structural**
  and dimensional axes. Only size/colour were ever compared. Structurally Todoist uses
  `<button class="task_checkbox" role="checkbox" aria-label="Mark task as complete">`; meologue
  uses `<label><input type="checkbox" readOnly aria-label={task.content}>`
  (`task-row-content.tsx:330-362`) — different element, different role, different accessible name.
  Dimensionally it is also now incomplete: **ring width varies by priority** (2px at P1, 1px at P4)
  and `task-row-content.tsx:348` hardcodes `1px` for every priority.
- **`CMT-06`** (`built`, "all nine templates verbatim") — **5 of 9 are verbatim.** The four carrying
  `{content}` (`format-event.ts:258,377,387,398`) wrap it in literal quotation marks; Todoist's own
  DOM renders a clickable content-preview chip with no quotes.
- **`QA-01`** (`matched`) — matched on *behaviour* (inline-block, padding appears/disappears) but not
  on the quoted pixel values: ours measure 29.41px/21.41px against Todoist's 32.31px/24.31px.
  Root cause below.
- **`KBD-06`** (`built`) — claims `todo-keymap.ts`'s header "names each key left out and why". It
  does not: `Z`/`⌘Z`, `⌘A`, arrows, `Esc` and `⌘⌥0` are absent with no acknowledgement. That silence
  is why `CMT-05`'s missing undo went unflagged.
- **`SCHED-01`** (`built`) — geometry matches byte-for-byte, but the evidence column never records
  that reaching the popover costs a bottom sheet plus a "Pick a date" button
  (`task-schedule-sheet.tsx:124-133,161-188`) — two layers Todoist does not have. Measuring the card
  while ignoring the path to it is precisely how a row reads healthy while the feature doesn't.

## 3. Rows that undersell what exists

- **`QA-09`**, **`QA-11`** — evidence `—`, status `todoist-captured`, yet both are fully implemented
  (`en.ts:61-70`, `date-rules.ts:165-186,206-226,241-260,94-136,375-388`,
  `quick-add-task.ts:123-131`). Bookkeeping staleness, not divergence.
- **`QA-14`** — its caveat ("apps/web's own `%`-sigil assumptions are untouched") describes a state
  that no longer exists; `promote-tasks.ts:93-104` already routes labels through the `@`-based

## 4. Confirmed defects, ranked by what a user actually sees

1. **Today prints a redundant date badge.** `today-view.tsx` renders `dueToday` through a plain
   `TaskRow` with no suppression path; `task-row-content.tsx:436-438` renders the badge whenever
   `task.date !== null`, which every row in that section satisfies. **Todoist omits the control from
   the DOM entirely.** Found independently by two passes.
2. **Today and Tomorrow are painted the wrong colour.** `format-task-date.ts` maps both to
   `--td-date-upcoming` (purple `rgb(169,112,255)`). Measured: Today `rgb(37,184,76)` green,
   Tomorrow `rgb(255,154,20)` orange. `DateTone` has no `"tomorrow"` member, so Tomorrow *cannot*
   be styled separately today. Falsifies `DATE-09`, unblocks `DATE-06`.
3. **Activity is unreachable on desktop.** `/todo/activity` is linked only from `todo-nav.tsx`
   (which hides itself at ≥900px) and from inside a Project. `todo-sidebar.tsx` — the nav that
   *replaces* it at that width — has no Activity link. Identical defect class to the Upcoming bug
   that shipped for a full release.
4. **The completion toast** — §1 above. Fires on every completion.
5. **`SCHED-02` quick options are stale.** Code implements `This weekend` (slot 3) · `Next week`
   (slot 4); live Todoist is `Next week` (slot 3) · `Next weekend` (slot 4).
   `task-schedule-popover.test.tsx:39-62,104-117` locks in the stale order, so tests change too.
6. **Completed tasks are segregated, not inline.** `completed-tasks.tsx` is a collapsed `<details>`;
   Todoist interleaves completed rows in the main list (measured: 7 active + 6 completed = 13
   `li[data-item-id]`). meologue's row checkbox is hardcoded `checked={false} readOnly`
   (`task-row-content.tsx:333`) — the list *structurally cannot* hold a completed row.
7. **Completed styling is wrong on two axes.** meologue paints the completed title
   `rgb(204,204,204)`; Todoist uses `rgb(128,128,128)` for the title and reserves `rgb(204,204,204)`
   for the date. And strikethrough is gated behind a Settings default of `"gray"` — **off** — where
   Todoist always strikes through.
8. **Quick Add is the wrong shape.** Todoist's is a `role="dialog" aria-label="Quick Add"` opened
   from a global button (580×66 empty, 580×97 once a date resolves, radius 12px, padding 16px).
   meologue's is a permanently-mounted inline row (`add-task-form.tsx:119-167`) with a 32px field,
   rendered **above** the list where Todoist's "+ Add task" sits **below** it.
9. **Activity log structure.** Todoist opens a separate "Task activity" modal with an
   "Added on {date} {time}" header, reached via More actions → View activity. meologue renders an
   inline `<details>` inside the already-open detail view; no "View activity" menu item exists.

## 5. Latent bugs found — not yet visible, but real

- **[parent-verified] Priority match-ids are inverted.** `matchIdForToken`
  (`todo-quick-add-recognition.ts:135-136`) returns `` `P${token.priority}` `` on the **stored**
  value, and `storedPriorityOf(ui) = 5 - ui` (`task-types.ts:333-335`). Typing `p1` emits
  **`P4`**. `task-types.ts:116-118` explicitly warns "never open-code `5 - priority`… use
  `uiPriorityOf`/`storedPriorityOf` to cross the inversion" — this function never crosses it. The
  test pins the wrong answer: `todo-quick-add-recognition.test.ts:79-81` asserts
  `{raw:"p1", priority:4}` → `"P4"`. Inert only because no priority chip renders it yet.
- **[parent-verified] The Quick Add field drops to 14px at desktop width.**
  `EDITOR_BOX_CLASSES` (`add-task-form.tsx:73-74`) ends `md:text-sm md:leading-[22px]` → 14px/22px
  against Todoist's measured 16px/23px. This is the root cause of `QA-01`'s width mismatch.
  **`index.css:574-575` already declares `--td-composer-title-font-size: 16px` and
  `-line-height: 23px` — with zero consumers.** The correct values sit in the file while the
  component hardcodes the wrong ones.
- **Dead tokens.** `--td-composer-background/-border/-radius` (`index.css:542-544,606`) and
  `--td-focus-ring` (`index.css:492`) have no consumers anywhere. A declared token is not an
  implementation.

## 7. Corrections to this audit's own findings

- **The `QA` pass called meologue's quick-add a "bottom-of-list row". It is not.**
  `AddTaskForm` is at `todo-page.tsx:701`, before `TaskList` at `:728` — it renders **above** the
  list. The agent was misled by `border-t border-border` (`add-task-form.tsx:120`), which looks like
  bottom-bar styling but is a top border on a block sitting above the list. Confirmed both in source
  and in a live browser snapshot. `NAV-10`'s characterisation stands.
- The `SCHED` pass corrected its own brief: `SCHED-11` was never `blocked` (it is
  `todoist-captured`), so it is not a candidate for reclassification.

## 8. Decisions this audit cannot make

1. **Does the corpus chase Todoist's live product, or pin to a capture date?** `SCHED-02` diverged
   not because code broke but because **Todoist shipped a change between 10 and 11 September**. This
   affects every row, not one.
2. **`QA-22` risk.** meologue ships a `{phrase}` deadline syntax. Todoist's actual deadline syntax
   was never captured in either pass, so this is an invention, not a match — and may be wrong.
3. **`QA-23`.** Plain `Enter` is treated identically to `Shift+Enter`. Todoist's plain-Enter
   behaviour was never isolated. Reasonable, unverified.

## 9. Side-by-side measurement — both apps driven

Everything above §9 was found by reading code against the corpus. This section is different: **both
applications were driven in a real browser at 1470×836, dark theme, and measured with
`getComputedStyle`.** That is the ledger's own bar for `matched`, and it had never been done.

**Measured as genuinely identical** — sidebar background `rgb(38,38,38)`, content pane
`rgb(31,31,31)`, plain row height 59px, row title 14px/21px `rgb(255,255,255)`, divider
`1px solid rgb(61,61,61)` full-width with 0 left inset, date control 12px, checkbox 18×18,
P4 ring 1px `rgb(169,169,169)`.

**Every divergence predicted from code was confirmed on screen:**

| # | Divergence | Measured |
|---|---|---|
| 1 | Today and Tomorrow | both `rgb(169,112,255)` purple vs Todoist's green `rgb(37,184,76)` / orange `rgb(255,154,20)` |
| 2 | Checkbox ring width | 1px at every priority vs Todoist's 2px at P1 |
| 3 | Today view | renders a redundant "Today" badge per row; Todoist omits the control from the DOM |
| 4 | Completed tasks | collapsed `<details>` "Completed (N)" vs Todoist's inline interleaving |
| 5 | Add-task field | above the list vs Todoist's "+ Add task" below it |
| 6 | Content column | **971px of a 1142px pane** (97%/85% proportional) vs Todoist's fixed **800px**; view name is an app-bar `<span>` ("Todo", 16px/500). **Zero `<h1>` elements exist anywhere in Todo's DOM** vs Todoist's in-column 26px/700 heading |

**Correction to §2 and §4 of this document.** The ring divergence is **width only** — P1's ring
colour does render `rgb(255,112,102)` correctly. Earlier sections say the ring is "hardcoded 1px",
which is accurate, but should not be read as the colour also being wrong. It isn't.

**Four divergences nobody predicted, found only by measuring:**

1. **The sidebar is not a 280px rail.** It is the chat layout's resizable "conversation list" pane
   (default ~306px), repurposed — so its width is user-adjustable where Todoist's is fixed.
2. **A completed row shows no date at all.** Not miscoloured — absent. Todoist renders it in
   `rgb(204,204,204)`.
3. **A completed title has no strikethrough**, and renders `rgb(204,204,204)` where Todoist uses
   `rgb(128,128,128)` + `line-through`. (Root cause in §4 item 7: strikethrough is gated behind a
   Settings default of `"gray"`, which is off.)
4. **Row height barely responds to content.** A row with a one-line description stays at 59px —
   content is vertically centred, so the row only exceeds the floor once a title wraps to 3+ lines,
   and even then reaches just 66px against Todoist's 100px.

**Not measurable:** P2/P3 ring colours — no such task exists in either app, and Todoist's own
reference for them was never captured (`PRI-06`, `blocked`). Nothing to compare.

**Method note for the next pass.** meologue's row divider is on an inner `[data-task-row-box]`, not
the `<li>` (which reports `0px`) — the same leaf-vs-wrapper trap that produced two contradictory
runs on the Todoist side. Measure the painted element, never its container.
